# Доповідь до захисту Cloud OCR

Надія Черниченко, ТТП-42. Орієнтовно 7–9 хвилин плюс демонстрація.

Текст описує поточний стан: реальний запит ще не перевірено. Після успішного виклику Google замініть відповідні речення фактичними результатами.

## Слайд 1. Cloud OCR

Добрий день. Я представляю PoC-проєкт Cloud OCR, який використовує Google Cloud Vision API для розпізнавання тексту на зображеннях. Мета роботи — показати інтеграцію власної програми з готовим хмарним сервісом штучного інтелекту. Я обрала OCR, тому що результат легко перевірити: є вихідне зображення і текст, який можна порівняти з ним.

## Слайд 2. Мета та межі PoC

PoC означає proof of concept, тобто перевірку працездатності ідеї. Користувач завантажує зображення, обирає режим і отримує текст. Це невеликий навчальний застосунок: він не має бази даних, облікових записів або підтримки багатосторінкових PDF. Такі межі дозволяють зосередитися на HTTP-запиті, автентифікації та обробці відповіді.

## Слайд 3. Платформа та обрані функції

Google Cloud надає обчислювальну інфраструктуру та готову модель. Vision також має функції аналізу інших ознак зображень, але в проєкті використано тільки OCR. TEXT_DETECTION підходить для написів, а DOCUMENT_TEXT_DETECTION орієнтований на щільний текст і повертає більш детальну структуру документа. Мій інтерфейс в обох випадках показує суцільний текст.

## Слайд 4. Архітектура застосунку

Браузер передає двійкові байти зображення на локальний маршрут /api/ocr. Сервер перевіряє розмір і сигнатуру файлу. Далі vision_client.py кодує байти в Base64 та формує JSON для Google. Після відповіді клієнт виділяє текст, а браузер показує його. Зображення не записуються сервером на диск. Хмарним компонентом є Vision API, хоча власний вебсервер запускається локально.

## Слайд 5. REST-запит до Google

REST API дозволяє звертатися до сервісу стандартними HTTP-запитами. Використовується метод POST, оскільки тіло запиту містить зображення. У requests є один об’єкт. Поле image.content містить Base64, а features визначає операцію. API key додається у параметр key, але не показується в інтерфейсі. Base64 не шифрує дані: це спосіб передати байти у JSON. Захист передавання забезпечує HTTPS.

## Слайд 6. Розбір відповіді та помилки

У відповіді Google клієнт читає перший елемент responses. Спочатку перевіряє, чи є помилка всередині цього елемента. Успішний HTTP-статус сам по собі не гарантує успішне розпізнавання. Потім береться fullTextAnnotation.text або запасне поле textAnnotations. Якщо тексту на зображенні немає, програма повертає порожній рядок. Мережеві збої та помилки доступу показуються зрозумілими повідомленнями без секретного ключа.

## Слайд 7. Налаштування та захист ключа

Щоб виконати реальний запит, потрібен власний Google Cloud project із налаштованим billing та активованим Vision API. Ключ обмежується цим API. У програмі він читається зі змінної середовища GOOGLE_VISION_API_KEY. Наявність ключа ще не доводить, що він чинний: доступ перевіряється під час реального запиту. Сервер запускається тільки на локальній адресі. Для публічного сервісу треба додати автентифікацію, контроль запитів та інший сервер.

## Слайд 8. Сценарій демонстрації

Під час показу потрібно чітко розрізняти два режими. Кнопка демоприкладу завжди показує одну підготовлену відповідь і потрібна для огляду інтерфейсу без ключа. Для підтвердження інтеграції слід завантажити sample.png та натиснути кнопку реального API. Після цього порівняти результат із expected.txt, особливо число 2026 і суму 125.50 UAH. На момент підготовки матеріалів реальний виклик ще не виконано, тому його результат і час не наведено.

## Слайд 9. Перевірка реалізації

Автоматичні тести перевіряють логіку програми. Наприклад, тест перевіряє, що після Base64-декодування отримуються початкові байти, що клієнт надсилає POST, і що ключ не потрапляє у текст помилки. Інші тести запускають локальний сервер та перевіряють його маршрути. Усього пройдено 18 тестів. Зовнішній сервіс підміняється контрольованою відповіддю, тому тести не потребують ключа. Вони не вимірюють точність Google Vision.

## Слайд 10. Сфери застосування

OCR корисний там, де дані є тільки на зображенні. Наприклад, можна перетворити фото конспекту на текст для пошуку або витягти текст чека. Але OCR сам по собі не визначає, яке число є підсумковою сумою. Для цього потрібен наступний модуль. Так само озвучення тексту є окремою функцією. Ці приклади описують можливі застосування API, а не всі можливості цього PoC.

## Слайд 11. Вартість та обмеження

Google рахує одиниці використання за зображеннями та функціями. Для обраних режимів сторінка тарифів указує безкоштовні перші 1000 одиниць на місяць і 1.50 долара за 1000 у наступному діапазоні до 5 мільйонів. Тарифи перевірено 5 листопада 2026 року, перед використанням їх потрібно звірити. Для PoC встановлено власний ліміт 4 MiB. Офіційні ліміти ширші: 20 MB на файл і 10 MB на JSON. Погане освітлення або розмиття можуть викликати помилки OCR.

## Слайд 12. Підсумок та джерела

У проєкті реалізовано приклад інтеграції з готовою хмарною моделлю. Основна частина роботи — підготувати запит, безпечно використати ключ, отримати та перевірити відповідь і показати результат користувачу. Для остаточного підтвердження наскрізного сценарію залишається виконати запит з власним ключем і зафіксувати результат. Код, інструкції та матеріали для захисту підготовлено. Дякую за увагу.

## Демонстрація на захисті

1. Запустіть сервер у терміналі з налаштованим ключем.
2. Відкрийте http://127.0.0.1:8000.
3. Оберіть samples/sample.png та TEXT_DETECTION.
4. Натисніть «Розпізнати через Google».
5. Покажіть статус «Реальний API», текст і час запиту. Не називайте його чистим часом роботи моделі.
6. Порівняйте текст з expected.txt, збережіть TXT.
7. Покажіть build_payload(), recognize() та extract_text() у vision_client.py.
8. Покажіть запуск тестів і репозиторій GitHub.

Якщо ключа або інтернету немає, покажіть демоприклад і прямо скажіть: «Це імітація відповіді для перевірки інтерфейсу, а не результат поточного виклику Google».

## Запитання викладача та короткі відповіді

**Що таке API?** Інтерфейс, через який одна програма запитує функції або дані іншої за визначеними правилами.

**Де тут хмара?** Модель розпізнавання працює на серверах Google. Мій Python-сервер лише передає запит та обробляє результат.

**Чому локальний сервер, якщо завдання про хмару?** У вимозі є інтеграція з хмарним API. Локальне розміщення клієнта не змінює місце виконання моделі.

**Що саме ви реалізували?** Інтерфейс, перевірку файлу, формування JSON, HTTPS-запит, розбір відповіді, помилки, експорт TXT і тести. Модель надає Google.

**Чому Python?** Для цього PoC достатньо його стандартних бібліотек. Запит до REST API видно без додаткового SDK.

**Для чого Base64?** Щоб представити байти зображення текстовим рядком усередині JSON. Це не шифрування.

**Чим відрізняється OCR від генерації тексту?** OCR витягує написані на зображенні символи. Проєкт не просить мовну модель створити новий текст або переказ.

**Чим відрізняються два режими?** TEXT_DETECTION призначений для написів, DOCUMENT_TEXT_DETECTION — для щільного тексту та структури документа. У цьому інтерфейсі обидва повертають суцільний текст.

**Що відбувається без ключа?** Реальний виклик завершується зрозумілою помилкою. Окрема кнопка демо повертає фіксовану fixture та позначає її як імітацію.

**Чому перевіряєте error за HTTP 200?** Пакетна відповідь може містити помилку окремого зображення, хоча сам HTTP-запит завершився успішно.

**Як захищено ключ?** Він зберігається у змінній середовища Python, відсутній у браузерному коді та не включається в повідомлення помилок. На стороні Google ключ треба обмежити потрібним API.

**Що означають 18 тестів?** Вони перевіряють поведінку нашої програми на контрольованих відповідях і роботу локальних маршрутів. Це не 18 реальних викликів Google і не оцінка точності OCR.

**Як виміряти якість?** Взяти набір зображень з ручним еталоном і порахувати частку помилок символів CER. Окремо зафіксувати правила пробілів і перенесень. У цій версії таких вимірювань ще немає.

**Чому 4 MiB?** Це обмеження PoC, щоб контролювати пам’ять і залишити запас під Base64 та JSON. Не слід називати його офіційним лімітом Google.

**Чи потрібен GPU на ноутбуці?** Ні. Модель виконує Google, ноутбук передає зображення та показує текст.

**Чому немає PARCS?** У вимозі завдання 2 немає обов’язкового використання PARCS. Обрано інтеграцію з API моделі штучного інтелекту.

**Як розвивати проєкт?** Додати чергу файлів, PDF, підсвічування координат слів, оцінку якості на наборі даних та production-розгортання з авторизацією.
